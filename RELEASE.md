# Как выпустить релиз

Регламент для человека, который делает это впервые. Порядок шагов не меняйте:
каждый следующий опирается на проверку предыдущего.

Пометки в командах: **[Mac]** — ваш компьютер, **[VM]** — боевой сервер
(`ssh yasa-vm`). Первый провижининг VM и секреты Actions — `deploy/CD.md`.
Инфраструктура и аварии — `docs/runbooks/deploy.md` (локальный).

## Что нужно иметь до начала

- права на push в репозиторий и на постановку тегов;
- в GitHub Actions заданы секреты `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`
  (см. `deploy/CD.md`);
- сервер один раз провиженен: Docker, deploy key, `.env.prod`, tessdata.

Ручной запасной путь с ноутбука по-прежнему работает: алиас `yasa-vm` в
`~/.ssh/config` и `NEUROLEGAL_DEPLOY_HOST=yasa-vm`, затем `make deploy`.
Проверка SSH, если идёте вручную. **[Mac]**

```bash
ssh yasa-vm 'hostname'
```

## Шаг 1. Посмотреть, что сейчас на проде

**[Mac]**

```bash
ssh yasa-vm 'cd /srv/neurolegal && git describe --tags && docker compose ps --format "{{.Service}}: {{.Status}}"'
```

Ожидается текущий тег и четыре сервиса в работе. Если какой-то сервис
`restarting` или `unhealthy` — сначала разберитесь с этим (раздел «Если
что-то пошло не так»), релиз поверх сломанного прода делать нельзя.

## Шаг 2. Убедиться, что код готов

Все правки должны быть в `main`. **[Mac]**

```bash
git checkout main && git pull
```

Проверки гоняет CI — на каждый push в `main` и на каждый тег. Локально то же
самое даёт `make check` (ruff, mypy strict, юнит-тесты), но это для быстрой
обратной связи: решает не он.

Красный CI означает, что релиза нет: сервер не выкатит тег без зелёной отметки,
да и сборка образа упала бы сама — фронт собирается с проверкой типов.

## Шаг 3. Поставить тег

Нумерация: `v0.1.1` — правки и мелочи, `v0.2.0` — новая функциональность.
Тег обязателен: сервер выкатывается именно по тегу, а не по ветке. **[Mac]**

```bash
git tag v0.1.1 -m "коротко, что изменилось"
```

```bash
git push origin main --tags
```

## Шаг 3а. Дождаться зелёного CI и автовыкатки

Push тега запускает прогон. Джобы: `backend`, `frontend`, на теге ещё `mark`
и `deploy`. `deploy` сама ходит на VM — `make deploy` с ноутбука не нужен.
**[Mac]**

```bash
gh run watch "$(gh run list --workflow=ci.yml --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status
```

Прогон занимает около четырёх минут на проверки плюс сборка образа на VM
(первый раз дольше). На зелёном `mark` появляется отметка
`refs/ci-passed/<коммит>` — без неё `deploy.sh` на сервере откажется. Смотреть:
вкладка Actions этого репозитория.

Если джоба `deploy` не стартовала — нет секретов `DEPLOY_*` или упал `mark`.
Разбор: `deploy/CD.md`. Запасной путь, когда Actions до VM не достучался:

```bash
make deploy TAG=v0.1.1
```

`deploy.sh` делает всё сам и в правильном порядке:

1. проверяет, что тег принадлежит `main` и на его коммите зелёный CI — без
   этого выкатка не начинается и сервер остаётся нетронутым;
2. переключает чекаут на тег;
3. собирает образ — старые контейнеры при этом **продолжают работать**;
4. проверяет наличие и права OCR-данных;
5. отказывается продолжать, если в rag выполняется ingest-джоб;
6. накатывает миграции;
7. пересоздаёт контейнеры;
8. проверяет `/healthz` четырёх сервисов и печатает команду откáта при неудаче.

Занимает 3–5 минут, из них простой — несколько секунд на пересоздание.
Активные ответы в чате в этот момент оборвутся, пользователю нужно повторить
вопрос.

**Скрипт выкатки едет вместе с кодом**, поэтому работает всегда та его версия,
которая лежит в текущем задеплоенном теге, а не в выкатываемом. Практическое
следствие: релиз, который меняет сам `deploy/deploy.sh`, проходит ещё старым
скриптом — его новые проверки включаются со следующей выкатки. Заметно это по
выводу: нет строки `==> гейт CI` — значит работает версия скрипта, которая
про гейт ещё не знает.

## Шаг 4. Проверить снаружи

**[Mac]**

```bash
curl -sS -o /dev/null -w 'сайт: %{http_code}, сертификат: %{ssl_verify_result}\n' https://yasa-tech.ru
```

Ожидается `сайт: 200, сертификат: 0`.

```bash
curl -sS -o /dev/null -w 'админка без пароля: %{http_code}\n' https://admin.yasa-tech.ru
```

Ожидается `401` — так и должно быть, вход только по паролю.

И глазами: откройте `https://yasa-tech.ru`, задайте в чате юридический вопрос
и убедитесь, что текст ответа появляется постепенно и содержит ссылки на
статьи. Это единственная проверка, которая покрывает всю цепочку сразу.

Наконец — запись в журнале. Она появляется на каждую выкатку, включая
неудачную и отклонённую. **[Mac]**

```bash
make deploy-history
```

Строка выглядит так: время, тег, предыдущий тег, откуда пришли, вердикт CI
(`passed`, `rollback`, `bypassed`, `blocked`), результат (`ok`, `fail`,
`refused`), длительность.

## Откат

Если после выкатки что-то работает не так — возвращаемся на предыдущий тег.
Это то же действие, никакой особой процедуры нет. **[Mac]**

```bash
make deploy TAG=v0.1.0
```

**База при откате не меняется.** Так и задумано: миграции в проекте только
аддитивные, поэтому предыдущая версия кода работает поверх новой схемы.
Откатывать миграции нельзя — они удаляют столбцы вместе с данными.

**Гейт CI откату не мешает.** Движение назад по истории — на любой тег, коммит
которого предшествует работающему, — разрешено всегда, в том числе на теги,
выпущенные до появления CI. Иначе гейт превращался бы в ловушку ровно в тот
момент, когда он опаснее всего.

## Если что-то пошло не так

Смотрите, на каком шаге остановился скрипт — он печатает причину.

| Что видите | Что делать |
|---|---|
| `ОТКАЗ: нет отметки CI на коммите тега` | Прогон ещё идёт или упал. Откройте ссылку из сообщения; если прогона не было — запустите вручную: `gh workflow run ci.yml --ref v0.1.1` |
| `ОТКАЗ: коммит тега не принадлежит origin/main` | Тег поставлен не на `main`. Слейте ветку в `main` и выпустите тег заново с новым номером |
| `ОТКАЗ: тег … не найден` | Забыт `git push --tags` |
| `ОТКАЗ: corpus/manifest.yaml изменён на сервере` | Манифест правили через админку. Закоммитьте правки в репозиторий либо отбросьте командой, которую печатает скрипт |
| `ОТКАЗ: в rag выполняется ingest-джоб` | Идёт загрузка кодекса. Дождитесь конца и повторите: прерывать нельзя, прод останется без поисковых индексов |
| `ОТКАЗ: нет tessdata/rus.traineddata` или про права | Выполните на сервере команды, которые печатает сам скрипт |
| Сборка падает на `tsc` | Ошибка типов во фронте. Релиза нет, чините код: `make check` локально |
| Сборка падает на загрузке пакетов | Обычно сетевое. Повторите команду; если повторяется — `docs/runbooks/deploy.md`, раздел «Известные грабли» |
| Миграции падают | Не выкатывайте дальше. Прод продолжает работать на старой версии, разбирайтесь с миграцией |
| Проверка `/healthz` красная | Скрипт печатает команду откáта. Сначала откатитесь, потом разбирайтесь |

Посмотреть, что происходит на сервере: **[VM]**

```bash
cd /srv/neurolegal && docker compose ps && docker compose logs --tail=100 agent
```

## Чего делать не нужно

- **Править файлы на сервере.** Он read-only копия тега; любая правка
  потеряется при следующей выкатке и разойдётся с кодом.
- **Откатывать миграции.** См. выше — это потеря данных.
- **Переставлять уже опубликованные теги** (`git tag -f`, force-push). Тег —
  единственная точка, по которой можно воспроизвести или откатить релиз.
- **Выкатывать без тега.** Скрипт этого и не позволит.
- **Обходить гейт «на всякий случай».** `ALLOW_UNVERIFIED=1 make deploy TAG=…` —
  только для случая, когда GitHub недоступен, а выкатить надо. Каждое
  использование видно в журнале как `ci=bypassed`.

## Что релиза не требует

| Задача | Как делается |
|---|---|
| Модель агента, промпты, параметры | В админке `admin.yasa-tech.ru`, применяется сразу |
| Догрузить или переиндексировать кодекс | На сервере: `docker compose run --rm rag neurolegal rag ingest --code "X" --bulk` |
| Поменять ключ или секрет | Правка `.env.prod` на сервере, затем `docker compose up -d` |
| Сбросить пароль пользователю | Вкладка «Пользователи» в админке |

Подробнее по каждому пункту, а также провижининг нового сервера, перенос
корпуса и разбор известных проблем — в `docs/runbooks/deploy.md` (файл
локальный, в репозиторий не попадает).

Тот же регламент для агента — `deploy/AGENT_DEPLOY.md`: вердикты гейта, таблица
отказов и запреты. Меняете порядок шагов здесь — правьте и там.
