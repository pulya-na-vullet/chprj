# P0: Документы пользователя + проверка договора на риски — дизайн

Дата: 2026-07-05. Статус: согласован в брейншторме.
Основание: `plan.md` (P0), `product/lawyer-assistant-research-2026-07-05.md`.

## Цель

Юрист загружает договор (DOCX или PDF, включая сканы) в чат, может задавать
по нему вопросы и запускать проверку на риски по плейбуку. Результат —
отчёт в беседе: таблица рисков с двойным цитированием (пункт договора ↔
статья закона) и карта покрытия плейбука. Позиционирование — «черновая
проверка, требует подтверждения юриста».

## Скоуп

Входит: загрузка DOCX/PDF, локальный парсинг (включая OCR сканов), таблица
`documents`, «чат с документом» (тул `read_document`), три плейбука
(услуги / поставка / аренда), пятистадийный пайплайн проверки, SSE-прогресс,
отчёт как сообщение беседы, рендер на фронте, тесты.

Не входит (позже): пакетная проверка N договоров (P2), redline/экспорт .docx,
пользовательские плейбуки через UI, сравнение версий, библиотека документов
вне беседы, фоновые джобы (см. «Решения» №1), анонимайзер.

## Ключевые решения

1. **Всё внутри чата** (подход A). Проверка — специальный ход `POST /chat`
   с полем `command`; прогресс и отчёт стримятся через существующий SSE,
   отчёт хранится в `messages`. Никакой новой job-инфраструктуры. Интерфейс
   движка (`ReviewEngine.run(document, playbook) → события/отчёт`) не знает
   про транспорт — при переходе на фоновые джобы (P2) меняется только
   обвязка.
2. **Парсинг полностью локальный.** DOCX — python-docx; PDF (текстовый слой
   и сканы) — LiteParse (`liteparse`, Apache-2.0, PDFium + Tesseract OCR,
   `rus`). Облачные парсеры не используются — документ не покидает сервер,
   в LLM уходит только текст. Продуктовый аргумент для пилотов.
3. **Плейбук — YAML в репо**, правила поддерживают и канонические проверки
   клауз, и произвольные текстовые требования (паттерн Noroots).
4. **Каждое правило закрывается явно** (`ok | risk | missing |
   not_applicable`) — молча пропущенных проверок не бывает (главный failure
   mode по ресёрчу — false negatives).
5. **Грaундинг рисков — только через существующий `rag_search`** (HTTP,
   boundary-правило agent↛rag соблюдено), с валидатором цитат: статья,
   отсутствующая в извлечённом, в отчёт не попадает.

## Архитектура

Новый модуль `src/neurolegal/agent/review/`:

- `parser.py` — фабрика парсеров по mime: `DocxContractParser`
  (python-docx), `PdfContractParser` (liteparse). Выход обоих — список
  абзацев/строк с метаданными.
- `sections.py` — общий билдер дерева секций из абзацев: нумерация
  «1.», «1.1.», «1.1.1» (regex, включая суффиксы), `preamble`/`trailing`
  спецсекции, char-offsets в `full_text`. Деградация: документ без
  нумерации → секции по заголовкам/абзацам.
- `playbook.py` — Pydantic-модели плейбука + загрузчик из
  `playbooks/*.yaml`.
- `engine.py` — `ReviewEngine`, пять стадий (ниже), эмитит события
  через тот же механизм, что `ChatAgent`.
- `report.py` — сборка `ReviewReport`.

Плейбуки: `playbooks/services_ru.yaml`, `playbooks/supply_ru.yaml`,
`playbooks/lease_ru.yaml` — по 15–25 правил, составляет Claude, валидирует
пользователь/юрист перед пилотом.

## Данные

Таблица `documents` (agent-owned, стиль `conversations`/`messages`:
String(36) UUID, generic JSON, SQLite-portable; Alembic-миграция):

| колонка | тип | примечание |
|---|---|---|
| id | String(36) PK | uuid4 |
| conversation_id | FK conversations.id, CASCADE | документ живёт в беседе |
| filename | String | оригинальное имя |
| content_hash | String | sha256, дедуп в рамках беседы |
| mime | String | docx / pdf |
| parser | String | `docx` \| `pdf` |
| status | String | `parsed` \| `failed` |
| error | Text nullable | текст ошибки парсинга |
| sections | JSON | дерево секций |
| full_text | Text | сквозной текст |
| created_at | DateTime(tz) | |

`messages` получает nullable JSON-колонку `review` (полный `ReviewReport`),
по паттерну `citations`/`web_sources`.

## API (все DTO — в `src/neurolegal/contracts/`)

- `POST /documents` — multipart: файл + опциональный `session_id`.
  Без `session_id` создаёт беседу (как `ensure_conversation`) и возвращает
  её id. Ограничения: `.docx`/`.pdf`, ≤ 20 МБ; нарушение → 422.
  Ответ `DocumentInfo`: id, session_id, filename, status, outline
  (номера + заголовки секций), error.
- `GET /documents/{id}` — `DocumentInfo` (для восстановления UI).
- `GET /playbooks` — список `{id, name, rules_count}` из загруженных YAML.
- `POST /chat` — `ChatRequest` + опциональное
  `command: {type: "risk_review", document_id, playbook_id}`.

OpenAPI-снапшоты + `npm run openapi:generate` — обычный гейт
(`test_contracts_openapi.py`).

## Пайплайн проверки (5 стадий)

1. **Маппинг** — один LLM-вызов (дешёвый): оглавление документа (номера,
   заголовки, первые строки) + правила плейбука → JSON
   `rule_id → [section_ids] | "not_found"` (structured output).
2. **Оценка** — на правило: question + полный текст его секций → structured
   output `{status: ok|risk|missing|not_applicable, risk_level, quote,
   explanation, recommendation}` (`not_applicable` — правило не относится
   к этому договору, напр. правило о доставке в договоре без доставки). `not_found` + `risk_if_missing` → риск «клауза
   отсутствует» (без LLM-вызова).
3. **Граундинг** — для рисков: `rag_search(rag_queries)` → цитаты
   «ст. N АКТ». Валидатор: цитата обязана присутствовать в извлечённом
   наборе, иначе отбрасывается (риск остаётся, но без нормы — помечается
   `no_basis`).
4. **Judge** — LLM-пас по каждому риску: `confirmed | overstated |
   not_a_risk`, один retry на невалидный ответ. Понижение видно в отчёте
   (поле verdict), молча не удаляется.
5. **Отчёт** — `ReviewReport{playbook_id, risks[], coverage[],
   disclaimer}`; риск: `{rule_id, level, verdict, contract_quote
   {section, text}, citations[], explanation, recommendation}`;
   coverage: каждое правило → `ok | risk | missing | not_applicable`.

Модели: всё на `NEUROLEGAL_LLM_MODEL`; env `NEUROLEGAL_REVIEW_MODEL` — опциональный
override для стадий 2 и 4. Ожидаемая длительность — 1–3 мин; SSE-прогресс
по правилам.

## Чат с документом

Если в беседе есть `parsed`-документы: в системный контекст добавляется
список документов с оглавлением (только заголовки); новый тул
`read_document(document_id, section_number?)` возвращает текст секции
(или всего документа, если он короткий). Тул доступен интентам `legal`
и `text_task`. Интент-классификатор не меняется.

## SSE-события (новые, в `contracts` + `events.py`)

- `review_progress`: `{rule_id, title, index, total, status}` — фронт
  рисует живой чек-лист.
- `review_report`: полный `ReviewReport`.
- Существующие `session`/`done`/`error` работают как раньше. Сообщение
  ассистента: `content` = короткое markdown-резюме (для истории/копипасты),
  `review` = полный JSON.

## Фронт

- Композер: скрепка (accept .docx,.pdf) → `POST /documents` → чип файла
  над композером; при отсутствии беседы фронт принимает `session_id` из
  ответа.
- Карточка документа в ленте: имя, статус, оглавление (свёрнуто), кнопка
  «Проверить на риски» → пикер плейбука (из `GET /playbooks`) → команда
  в `/chat`.
- Прогресс: чек-лист правил (тихая анимация, Alfa-язык: монохром + красный
  акцент, без кричащих плашек).
- Отчёт: таблица рисков по уровням (high → low), в строке — цитата
  договора, норма (кликабельна в существующую панель источников),
  рекомендация; отдельно — карта покрытия; дисклеймер.
- История: `GET /conversations/{id}/messages` отдаёт `review` — отчёт
  восстанавливается при перезагрузке.

## Ошибки

- Формат/размер → 422 с человекочитаемым текстом.
- Парсинг упал → `status=failed` + `error`; карточка показывает ошибку;
  беседа работает дальше.
- Скан без Tesseract → ошибка парсинга этого файла с понятным текстом
  («OCR недоступен»), не влияет на обычные PDF.
- LLM-сбой в середине проверки → SSE `error`, отчёт не сохраняется,
  на карточке «повторить». Лок беседы снимается (существующий finally).
- Повторная проверка того же документа — разрешена (новое сообщение).

## Тесты

- Юниты: `sections.py` на фикстурах (нумерованный договор, договор без
  нумерации, суффиксы «1.1-1»); DOCX-парсер на фикстуре .docx; загрузчик
  плейбуков валидирует все `playbooks/*.yaml` (id уникальны, поля полны);
  движок на фейковом LLM: happy path, «модель процитировала статью вне
  извлечённого» (валидатор режет → `no_basis`), «каждое правило закрыто
  в coverage», judge-понижение видно в отчёте; LiteParse в юнитах мокается.
- Интеграция `api_with_mocks`: аплоад (ok/422/failed-парсинг), чат-команда
  end-to-end с фейковым движком.
- Гейты: OpenAPI-снапшоты + TS-генерация; boundary-тест agent↛rag
  покрывает `agent/review/` автоматически.

## Критерии приёмки

1. Загрузка DOCX и PDF (вкл. скан при установленном Tesseract) → карточка
   с оглавлением.
2. Вопрос по документу в чате → ответ с опорой на `read_document`.
3. «Проверить на риски» на реальном договоре услуг → отчёт за ≤ 3 мин:
   ≥ 1 риск с цитатой договора и валидной нормой, карта покрытия закрывает
   все правила плейбука.
4. Обрыв LLM в середине → понятная ошибка, повторный запуск работает.
5. `make check` зелёный; OpenAPI-снапшоты и бандл фронта пересобраны.
